# Test technique Blissim — Dev Backend

Ce dépôt contient les deux parties du test :

1. **Partie SQL** : [`blissim.sql`](blissim.sql) (schéma e-commerce, données de test, les deux requêtes demandées).
2. **Partie PHP** : une application Symfony 7.4 qui affiche le catalogue de [fakestoreapi.com](https://fakestoreapi.com/products) et permet d'ajouter, modifier et supprimer des commentaires sur chaque produit (stockés en PostgreSQL via PDO).

## Prérequis

- Docker et Docker Compose v2

C'est tout : PHP 8.3, Composer et PostgreSQL 17 tournent dans les conteneurs.

> Sans Docker : PHP 8.2+ avec les extensions `pdo_pgsql`, `intl`, `xml`, `mbstring`, Composer 2 et un PostgreSQL 12+ (voir [Lancer sans Docker](#lancer-sans-docker)).

## Installation et lancement

```bash
git clone <url-du-depot> blissim && cd blissim
docker compose up -d --build
```

Au démarrage, le conteneur `app` installe les dépendances Composer (environ 30 secondes au premier lancement), importe le catalogue FakeStore dans la base, puis l'application est disponible sur **http://localhost:8000**.

Pour suivre le démarrage : `docker compose logs -f app`.

Pour arrêter : `docker compose down` (ajouter `-v` pour supprimer aussi les données PostgreSQL).

> Sous Linux, si votre utilisateur n'a pas l'uid 1000, lancez `UID=$(id -u) GID=$(id -g) docker compose up -d --build` pour que les fichiers `vendor/` et `var/` vous appartiennent.

## Base de données

| Paramètre | Valeur |
|---|---|
| Hôte (depuis la machine) | `127.0.0.1:5433` |
| Hôte (depuis le conteneur `app`) | `db:5432` |
| Utilisateur | `app` / `app` |
| Base | `blissim` |

Une seule base, `blissim`, partagée par les deux parties :

- `product` : copie locale du catalogue FakeStore, et produits propres à l'application ;
- `customer`, `customer_order`, `order_item` : les commandes de la partie SQL ;
- `comment` : les commentaires de l'application, avec une clé étrangère vers `product`.

Elle est créée au premier démarrage par le conteneur PostgreSQL, qui exécute automatiquement `blissim.sql`. Le catalogue est ensuite complété par l'import (voir ci-dessous).

## Partie SQL

Le fichier s'exécute dans la base courante (il supprime puis recrée ses tables) et peut être rejoué à tout moment. **Attention : il réinitialise toute la base**, commentaires compris. Relancer ensuite l'import pour retrouver le catalogue complet :

```bash
docker compose exec -T db psql -U app -d blissim < blissim.sql
docker compose exec app php bin/console app:import-products
```

Les deux requêtes sont à la fin du fichier, et leur résultat s'affiche. Pour les lancer à la main :

```bash
docker compose exec db psql -U app -d blissim
```

Choix de modélisation :

- `customer`, `product`, `customer_order` (car `ORDER` est un mot réservé), `order_item`, `comment`.
- Un produit a trois identifiants :
  - `id` : identifiant de l'application (`GENERATED BY DEFAULT AS IDENTITY`), seul référencé par les clés étrangères ;
  - `source` : origine du produit (`'fakestore'`), `NULL` pour un produit créé dans l'application ;
  - `supplier_product_id` : identifiant du produit chez la source, en `VARCHAR` pour accepter le SKU ou l'UUID d'une autre source.

  `UNIQUE (source, supplier_product_id)` sert de clé à l'import, et un `CHECK` impose que les deux colonnes soient renseignées ensemble. Deux sources peuvent donc avoir chacune un produit « 1 » sans collision. Le jeu de données reprend six produits réels de FakeStore et un produit sans source.
- Les montants sont stockés **en centimes, dans des entiers** (`INTEGER`) : 109,95 € est stocké `10995`. Les calculs sont exacts, sans erreur d'arrondi, et les valeurs se manipulent en `int` côté PHP. Un `CHECK` interdit les prix négatifs.
- `order_item.unit_price_cents` fige le prix payé : `product.price_cents` peut évoluer à chaque import sans modifier l'historique. Le seed le montre avec le produit 1, vendu 99,95 € puis 109,95 €.
- Contraintes : clés étrangères, `UNIQUE` sur l'email, `CHECK` sur les quantités et sur le statut des commandes, `UNIQUE (order_id, product_id)` (un produit apparaît une seule fois par commande, avec sa quantité).
- Suppressions : supprimer une commande supprime ses lignes, supprimer un produit supprime ses commentaires (`CASCADE`). En revanche, on ne peut pas supprimer un client ou un produit présent dans une commande (`RESTRICT`).
- Chaque table a deux colonnes techniques gérées par la base : `created_at` (`DEFAULT CURRENT_TIMESTAMP`, date de création de la ligne) et `updated_at` (date de dernière modification). PostgreSQL n'ayant pas d'équivalent à `ON UPDATE CURRENT_TIMESTAMP`, `updated_at` est tenu par un trigger, `set_updated_at`, qui ne la change que si une valeur de la ligne change. L'application ne les écrit jamais. `customer_order.ordered_at` reste la date métier de la commande, utilisée par les requêtes.
- Les clés étrangères sont indexées explicitement (PostgreSQL ne le fait pas automatiquement).
- Les dates du seed sont relatives à `NOW()`, pour que la requête « 7 derniers jours » donne toujours le même résultat.
- La requête 2 exclut les commandes annulées, qui ne sont pas des ventes.

## Partie PHP

### Fonctionnalités

- `bin/console app:import-products` : importe ou met à jour le catalogue FakeStore dans la table `product` (lancé automatiquement au démarrage du conteneur).
- `/` : liste des produits (titre, image, prix).
- `/products/{id}` : fiche produit (`id` de l'application, celui de la table `product`), liste des commentaires et formulaire d'ajout.
- `/comments/{id}/edit` : modification d'un commentaire.
- `POST /comments/{id}/delete` : suppression, protégée par un jeton CSRF.

### Architecture

```
src/
├── Command/           ImportProductsCommand (app:import-products)
├── Controller/        ProductController (catalogue, fiche, ajout de commentaire), CommentController (édition, suppression)
├── Repository/        ProductRepository (copie locale, upsert), CommentRepository (requêtes PDO)
├── Service/           ProductImporter (import du catalogue en une transaction)
│   └── Provider/      ProductProviderStrategyInterface, FakeStoreProviderStrategy (stratégie FakeStore, appels HTTP),
│                      CachedProductProvider (cache, décorateur)
├── Dto/               CommentData (données du formulaire + validation)
├── Database/          Database : connexion PDO ouverte au premier usage, exécution des requêtes préparées
├── Model/             Product, Comment (objets en lecture seule)
├── Form/              CommentType
├── Twig/              MoneyExtension (affichage des prix en centimes)
├── Exception/         ProductApiException, ProductNotFoundException, DatabaseException
└── EventListener/     ServiceUnavailableListener : API ou base indisponible → page 503
templates/             Twig + Bootstrap 5
tests/                 Unit, Integration (repositories sur PostgreSQL), Functional (WebTestCase, commande)
```

### Gestion des erreurs

| Situation | Comportement |
|---|---|
| API lente ou injoignable | timeout de 5 s, 2 nouvelles tentatives, puis page 503 « catalogue indisponible » |
| API en erreur 5xx, JSON invalide ou structure inattendue | page 503, erreur détaillée dans les logs |
| Produit inexistant (l'API répond 200 avec un corps vide) | 404 |
| PostgreSQL arrêté | page 503 (les pages ont besoin de l'`id` des produits, enregistré en base) |
| Formulaire invalide | réaffiché avec les erreurs (HTTP 422) |

Les réponses de l'API sont mises en cache 10 minutes. Une erreur n'est jamais mise en cache.

### Lien entre l'API et la base

Les pages lisent les produits dans l'API (avec cache), qui reste la source de vérité. La table `product` en est la copie locale, utilisée par les commandes et les commentaires (clés étrangères). Elle est alimentée de deux façons :

- **import complet** par `app:import-products`, en une transaction (tout ou rien) ; si l'API échoue, la base n'est pas modifiée ;
- **à la volée** : le catalogue (`/`) enregistre les produits renvoyés par l'API (upsert), et la fiche réenregistre le produit qu'elle affiche. L'import n'est donc pas un prérequis.

L'upsert (`INSERT … ON CONFLICT … DO UPDATE … RETURNING id`) se fait sur `(source, supplier_product_id)` et renvoie l'`id` de l'application en une seule requête. C'est lui qui figure dans les URL (`/products/{id}`) et que référencent les commentaires : la fiche retrouve le produit en base par cet `id`, puis demande sa version à jour à l'API avec son `supplier_product_id`. Un produit sans source (créé dans l'application) a lui aussi une fiche.

## Tests

```bash
docker compose exec app php bin/phpunit
```

Les tests n'appellent jamais la vraie API, et ne touchent pas à la base de développement :

- l'API est simulée (`MockHttpClient` et `tests/Support/FakeStoreMockResponseFactory.php`) ;
- les tests qui utilisent la base travaillent sur une base PostgreSQL dédiée, `blissim_test`, créée si besoin puis réinitialisée avant chaque test à partir de `blissim.sql` : on teste le vrai schéma livré, clés étrangères comprises. Le conteneur `db` doit donc être démarré.

## Xdebug

Xdebug 3 est installé dans l'image mais désactivé par défaut, pour ne pas ralentir l'application. Son mode est piloté par la variable `XDEBUG_MODE`.

**Débogage pas à pas** (port 9003) :

```bash
XDEBUG_MODE=debug docker compose up -d
```

Dans PhpStorm :

1. Créer un serveur nommé `blissim` (Settings > PHP > Servers), hôte `localhost`, port `8000`.
2. Activer « Use path mappings » : racine du projet → `/app`.
3. Cliquer sur « Start Listening for PHP Debug Connections ».

Sous VS Code (extension PHP Debug), configuration `launch.json` :

```json
{ "name": "Xdebug (Docker)", "type": "php", "request": "launch", "port": 9003,
  "pathMappings": { "/app": "${workspaceFolder}" } }
```

Chaque requête HTTP se connecte à l'IDE (`start_with_request=yes`). Pour déboguer les tests :

```bash
docker compose exec -e XDEBUG_MODE=debug app php bin/phpunit
```

**Couverture de code des tests** :

```bash
docker compose exec -e XDEBUG_MODE=coverage app php bin/phpunit --coverage-text
```

Pour désactiver Xdebug : `docker compose up -d`, sans la variable.

## Lancer sans Docker

```bash
composer install
# Adapter la connexion dans un fichier .env.local, par exemple :
# DATABASE_DSN="pgsql:host=127.0.0.1;port=5432;dbname=blissim"
createdb blissim
psql -d blissim < blissim.sql
php bin/console app:import-products
php -S 127.0.0.1:8000 -t public
```

Pour les tests hors Docker, adapter l'hôte et les identifiants PostgreSQL dans `phpunit.dist.xml` (copié en `phpunit.xml`, ignoré par git).

## Pistes d'amélioration

- Authentification, pour que seul l'auteur d'un commentaire puisse le modifier ou le supprimer.
- Pagination des commentaires.
- Migrations versionnées (Doctrine Migrations, ou outil équivalent avec PDO) au lieu d'un script d'initialisation.
- Accélérer les tests : recréer la base une seule fois et isoler chaque test dans une transaction annulée à la fin.
- Lancer l'import périodiquement (cron ou Symfony Scheduler) et lire les pages depuis la base plutôt que depuis l'API.
- Image de production : PHP-FPM + Nginx, `composer install --no-dev`, `APP_ENV=prod`.
